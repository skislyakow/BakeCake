## Принцип отбора фич

**Работаем строго по ТЗ** (см. раздел «ТЗ» — исходное техническое задание). Всё, чего
нет в ТЗ, в MVP не делается — даже если выглядит красиво и стоит 150 строк кода.

Второй принцип, появившийся из-за срока: **работающий сценарий важнее красивого
экрана.** Лучше рабочий конструктор без анимаций, чем красивый лендинг без заказа.

Допускаются только два исключения:

1. **Дешёвые технические решения** там, где ТЗ требует результат, но не говорит как:
   `loading="lazy"` и `width/height` против CLS, `min`/`max` на полях даты и времени
   вместо своего списка интервалов, gunicorn + nginx вместо `runserver`.
2. **Админская настройка** вместо хардкода: цены и промокоды правятся в админке,
   а не меняются в коде. Время доставки — обычное поле заказа, отдельного справочника
   не вводим (раздел 6).

Всё остальное, что придумали «для удобства» (визуальный предпросмотр торта, отдельная
группа «Начинка», базовая цена, корзина, бонусная программа) — **за рамками MVP**.

**Открытый риск, который этим решением не закрывается:** из ТЗ «торт слишком сложно
заказать». Компенсируем тем, что уже есть: допы в один клик вместо выпадающих списков,
живой пересчёт цены, обязательные поля помечены, телефон в шапке, JivoSite-виджет. Проверяем
в воскресенье на человеке не из команды — если отказы будут, предпросмотр вернём
отдельной задачей.

### Контекст

Магазин тортов на заказ. На данный момент магазин имеет несколько стандартных тортов,
но также принимает заказы на торты, собранные самим покупателем. Основной источник
продаж — Instagram.

Сейчас компания хочет запустить рекламу на других платформах: Яндекс, сайты с
рецептами, сайты для заказа аниматоров на праздник. Нужно создать сайт для тестирования
новых рекламных каналов. Важно соотношение цена/качество: нужно быстро сделать MVP,
чтобы заказчик смог оценить перспективность этого направления.

При этом откровенно плохое оформление сайта может испортить весь эксперимент, поэтому
оно особенно важно.

> **Стоимость заказа — 140 000 ₽.** В исходнике написано «140 000 тысяч рублей»,
> по смыслу это 140 тысяч; уточнение зафиксировано в разделе 17.

### Ценность

**Для клиента:**

- Способ удивить гостей на празднике (свадьба, день рождения, корпоратив)
- Возможность заказать себе вкусный десерт
- Простой способ проявить внимание человеку, у которого праздник

**Для владельца приложения:**

- Получить новый источник заказов
- Автоматизировать приём заказов — не по телефону через удалённого менеджера
  по продажам, а автоматически

### Ограничения

- Дешёвая разработка, режется почти весь функционал ради дешёвого эксперимента
- Большой упор на визуальную составляющую
- Сам приём заказов в обязательном порядке должен быть реализован
- Торты можно модифицировать на свой вкус, заказывать надписи и состав
- Приложением удобно пользоваться с телефона
- В приложении много картинок с красочными тортами

## 1. Стек и инфраструктура

| Слой | Решение | Почему |
|---|---|---|
| Бэкенд | **Django 5 + DRF** | Курс DVMN «Профессия Middle Python/Django разработчик» |
| БД | **SQLite — стандартная БД Django по умолчанию** | Решение команды: учебный проект, лишних сущностей быть не должно |
| Фронт | **Текущий Vue 3 (CDN) + Bootstrap 5**, обёрнут в Django-шаблоны | Дизайн не трогаем, diff минимальный |
| Хостинг | **FirstVDS, Ubuntu 24.04**: nginx + gunicorn + systemd | Сервер уже есть у команды, показываем на нём |
| SSL | Let's Encrypt (certbot) | Бесплатно, обязателен для ЮKassa и JivoSite |
| Оплата | **ЮKassa (YooMoney): готовый платёжный виджет + вебхук** | Свою форму оплаты не пишем |
| Чат | **JivoSite**, бесплатный тариф | Иконка `img/intercom.svg` уже есть в макете, нужен только ID |
| SMS | **Не нужна** — вход по любому номеру телефона | Убирает внешний сервис целиком |

### Почему SQLite

Решение команды, и оно правильное для учебного проекта:

- **В `settings.py` остаётся дефолт Django** — ноль строк конфигурации БД. Заодно
  меньше мест, где можно ошибиться.
- **Нулевые требования к серверу.** Ни `mysql-server`, ни создания пользователя, ни
  `CREATE DATABASE`. `manage.py migrate` работает сразу после клонирования.
- **Нулевые требования к разработчикам.** Трое на Windows не настраивают БД.
- **Перенос БД — это копирование одного файла** `db.sqlite3`. Бэкап — `cp`, восстановление
  — `cp`. Никаких `mysqldump`.
- **Всё, что делает сайт, влезает в десятки мегабайт.** Заказы, визиты, промокоды —
  для эксперимента с рекламой это единицы записей в день.

**Обязательная настройка в `settings.py` (одна строка, делает А в первый день):**

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
        "OPTIONS": {"timeout": 20},   # ждать блокировку вместо ошибки "database is locked"
    }
}
```

Плюс включаем **WAL-режим** (права на запись не блокируют чтение):

```python
from django.db.backends.signals import connection_created
def enable_wal(sender, connection, **kwargs):
    connection.cursor().execute("PRAGMA journal_mode=WAL;")

connection_created.connect(enable_wal)
```

**Честно о границе.** SQLite плохо переносит много одновременных записей. Наш сценарий —
десятки заказов в день плюс вебхуки ЮKassa: это единицы записей в секунду, запас
десятикратный. Если бы сайт вырос до тысяч заказов в день, миграция на PostgreSQL — это
одна секция в `settings.py` плюс выгрузка через `dumpdata`/`loaddata`. Но это уже не
учебный проект, и в этот срок точно не наша задача.

### Почему без Docker

Docker обсуждался и **сознательно убран**. При сроке 7 дней и трёх разработчиках он
съедает время на то, что не является целью проекта: volume-права, зависимости между
контейнерами, отладка «почему контейнер не видит код». У нас один сервис, одна БД,
масштабирование не планируется.

Вместо этого классический деплой: systemd-юниты на `gunicorn`, nginx как системный
пакет, сертификат certbot. Плюс к этому мы реально понимаем, что происходит на сервере, —
для учебного проекта это полезнее, чем спрятать за абстракцией.

Docker можно добавить позже одной командой, когда сайт работает.

### Правила ветвления

| Правило | Как читается |
|---|---|
| `main` | Единственная деплоимая ветка. Крон на сервере тянет её (раздел 12) |
| Ветка на шаг | `step-<NN>-<короткое-имя>`: `step-01-backend-skeleton`, `step-13-create-order`. Номер — шаг из раздела 13, чтобы ветка и конвейер читались как одно |
| Один шаг = одна ветка = один мерж | Закрыл шаг → мержишь в `main` → ставишь галочку. Ничего не копится |
| Ветка живёт максимум день | Пережил сутки — разбирай, не тащи. Дейли без мержа съедают параллелизм, ради которого ветки и затевались |
| В `main` — только мерж | Fast-forward запрещён: `git merge --no-ff`. История должна показывать шаги, а не отдельные коммиты |
| Конфликт решает владелец файла | Не автор мержа (раздел 2, колонки «ВЛАДЕЛЕЦ») |
| Отметка в конвейере | `(back, step-13, коммит a1b2c3d)` — роль, ветка, коммит |

**Почему конфликтов почти не будет.** Владение файлами уже разделено: `config/` — А,
`templates/` и `static/` — Б, `deploy/` — В. Пересекается ровно один файл —
`admin.py` в семи приложениях: А регистрирует модели в шаге 2, В вешает свои экраны
«Сводка» и «Доска заказов» в шагах 19–20. **В `admin.py` не лезет вообще:** свои экраны
делает через `get_urls()` + отдельный `views.py` в `analytics`. Обсудить это в чате
до начала, а не разбираться в середине недели.

**Что не делаем:** не форкаем ветку от `dev`, не держим долгоживущие `develop`,
не настраиваем `git-flow` — на 7 дней и троих это лишние правила, которые придётся
объяснять новичкам.

**Почему статусов ровно три.** В вёрстке (`lk-order.html:139,170`) захардкожены всего два
подписанных состояния: «Статус: В доставке» и «Статус: Выполнен». В ТЗ статусов нет
вообще — только «узнать сроки доставки» и «новые сроки». Поэтому берём минимум, который
не даёт потерять заказы:

- `new` — создан, ждёт предоплаты. Нужен, чтобы отличать неоплаченный заказ от оплаченного.
- `paid` — вебхук ЮKassa `payment.succeeded`. Единственный переход по автоматике.
- `delivered` — отмечает админ, когда торт отдан клиенту. Подпись «Выполнен» — как в макете.

**Отмены нет:** работаем только по предоплате, поэтому заказ, оплаченный и переданный в
работу, отменить нельзя — деньги уже у пекарни. Статус `cancelled` и кнопка отмены в
проекте отсутствуют; возврат делается вручную, вне системы.

**Промежуточных статусов нет** (`cooking`, `ready`, `delivering`): в источниках их нет,
а вручную проставлять их на демо никто не будет. Производственные этапы пекарня видит по
оплаченным заказам в админке — сортировка по `delivery_date` и есть очередь.

**Перенос срока — не статус.** `rescheduled` как значение `status` ломал цепочку. Вместо
него два поля: `is_rescheduled: bool` + `reschedule_note: str`. Статус при этом не меняется.

```

GET  /api/orders/                   мои заказы
GET  /api/orders/<number>/          состав, статус, срок доставки  ← «повторить» = фронт берёт spec отсюда
POST /api/orders/<number>/issue/    жалоба / запрос новых сроков
POST /api/payments/<order_id>/      создать платёж ЮKassa → confirmation_url
POST /api/yookassa/webhook/         payment.succeeded → статус «оплачен»
POST /api/track/visit/              UTM-пинг
— staff —
GET  /api/admin/orders/             список + фильтры (статус, дата, utm_source)

```

**Ключевое правило:** цену считает только бэкенд. Фронт показывает предварительную сумму
для эффекта, но заказ создаётся по серверному расчёту.

## 4.1 API-контракт (замораживается во вторник до 14:00)

Это главный артефакт для параллельной работы. Контракт живёт **здесь, в плане**, и
замораживается **вместе с рабочими заглушками** во вторник до 14:00. Отдельный
`docs/API.md` не заводим: дублировать этот раздел — тратить день, которого нет.
Фронт и админка пишутся сразу после этого, не дожидаясь реализации.

Правила контракта:

- **Формат — один и тот же для всех**: `{ok: true|false, error: "текст на русском"}` плюс
  полезная нагрузка. Фронт никогда не парсит текст ошибки, только `error` для показа.
- **Все эндпоинты возвращают `200`, даже заглушки.** Не `404`, не `501`. Пустой список
  и нули — валидный ответ.
- **Ошибки валидации — список**, а не одна строка:
  `{"ok": false, "errors": {"phone": "Введите номер телефона"}}` — Б рисует их у полей
  существующими классами `.cake_pink`, которые в макете уже есть для этого.
- **Даты — ISO**, `2026-10-05`. Время — `HH:MM`. Суммы — целые рубли (в ТЗ цены целые,
  рубли — проще и не спорим с заказчиком).
- **Порядок расчёта суммы жёстко зафиксирован**, иначе фронт с бэком посчитают по-разному:
  1. сумма торта = база + допы (`subtotal`)
  2. если срочный — `rush_amount = round(subtotal * 0.20)` (п. 9 ТЗ)
  3. промокод — процент от `subtotal + rush_amount`
  4. `total = subtotal + rush_amount - discount`
- **`is_rush` и `rush_amount` считает только сервер** и никогда не берётся из тела запроса.
  Клиент может прислать что угодно — это единственный способ не дать снять наценку вручную.
- **`delivery_time` проверяется на сервере**: `DELIVERY_FROM ≤ время ≤ DELIVERY_TO`.
  `min`/`max` в `<input type="time">` — удобство, а не защита.
- **CSRF-токен** передаётся в `<meta name="csrf-token">` в `base.html`, забирает его
  общая JS-функция. Отдельной файл не нужно.

## 6. Пункт 10 из ТЗ — «Время доставки»: что делать и как

**Исходное состояние.** В макете уже есть оба поля: `index.html:308,378` —
`<input type="date">` и `index.html:309,379` — `<input type="time">`. Ничего нового в
разметку не добавляем. Проблема в другом: сейчас там нет ни ограничения окна, ни правила
«изготовление 24 ч», ни предупреждения о срочности. Всё это — валидация, не дизайн.

**Что делаем:**

1. **Окно доставки 10:00–23:00 — берём из макета** (`index.html:170` «с 10:00 до 23:00»,
   без «приёма до 20:00» — время в проекте интересует только доставки, режим работы
   из `index.html:41` в правила не входит).
   - На клиенте — `.cake__textinput` и так уже есть; добавляем `min="10:00"` и
     `max="23:00"` к существующему `<input type="time">`, `min="сегодня"` к дате.
     Браузер не даст ввести 03:00 — по ТЗ достаточно, отдельный список не строим.
   - На сервере — проверка в `POST /api/quote/` и `POST /api/orders/`: время вне окна
     → `{ "errors": { "delivery_time": "Доставка работает с 10:00 до 23:00" } }`.
     `min`/`max` на клиенте — удобство, защита только серверная.

2. **Правило 24 часов и надбавка +20% (п. 9 ТЗ, `index.html:155-156`).**
   `deadline = now + 24 ч`. Если `выбранные дата + время < deadline` → заказ срочный:
   **в БД пишем `is_rush = True` и `rush_amount = subtotal * 0.20`**, в `/api/quote/`
   сумма пересчитывается и рядом с временем показывается текст «Срочный заказ, +20%».
   Объяснение двух моментов:
   - **Предупреждение текстовое, не блокирующее** — чекбокса подтверждения нет. Клиент
     видит наценку в итоге до отправки, ТЗ требует только «увеличивает стоимость на 20%».
   - **Пометка в БД обязательна**, а не только в ответе: админ в карточке заказа сразу
     видит, что заказ срочный, и пекарь учитывает это в очереди.

3. **Срочность считает сервер, всегда.** При создании заказа и в `/api/quote/` `is_rush`
   не берётся из тела запроса, а вычисляется заново по `now`. Так клиент не снимет
   наценку вручную и не получит старую цену после долгого раздумья.

4. **Очередь пекарни — не статусы, а дата.** Сортируем оплаченные заказы по
   `delivery_date` + `delivery_time`; срочные (`is_rush`) — с меткой «+20%» в карточке.
   Отдельного статуса «готовится» нет — в ТЗ и макете его нет (раздел 13, задача 16).

5. **Фиксируем в заказе:** `delivery_date` + `delivery_time` — **обычные поля, без
   справочника и снапшотов.** Правка времени админом не ломает заказ: время — это
   данные о заказе, а не ссылка на интервал. Снэпшот нужен был только для слотов.

6. **Перенос доставки админом закрывает две фичи сразу.** Кнопка «Перенести» →
   `OrderEvent(kind='rescheduled', text='Новые сроки доставки: 16:00')` +
   `is_rescheduled = True` + `reschedule_note`. **Статус при этом не меняется** — заказ
   остаётся `paid`. Пользователь в ЛК и на странице заказа видит баннер с новыми сроками.
   Это ровно сценарий «узнать новые сроки доставки».

7. Время: `TIME_ZONE = 'Europe/Moscow'`, `USE_TZ = True`. В БД UTC, в интерфейсе московское.

## 7. Оплата ЮKassa — сценарий

1. Чек-аут → «Оплатить N ₽» → `POST /api/payments/<id>/` → виджет ЮKassa
   (`https://yoomoney.ru/checkout/widgets/quickpay?widgetKey=<SHOP_ID>`) с
   `success_redirect_url` на `/lk/?order=<номер>&paid=1` — ЛК открывает модалку этого
   заказа. **`paid=1` в URL — только признак «пользователь вернулся», сам по себе
   статус не меняет:** ЛК читает фактический статус из `GET /api/orders/<number>/`.
2. Вебхук `payment.succeeded` (с проверкой IP-адресов YooKassa и `Idempotence-Key`) →
   заказ `paid`, пишем `OrderEvent`. **Это единственный штатный путь в «Оплачен».**
3. **Страховка эксперимента:** если пользователь закрыл окно оплаты, заказ висит в статусе
   `new` и виден в админке с кнопкой «Отметить оплаченным вручную». Реклама не должна
   съедать заказы из-за платёжного сбоя.
4. **ЛК (возврат) верит только API.** Пришёл `?paid=1`, а вебхук не успел — статус
   ещё `new`. Не показываем «Оплачен» до подтверждения: в модалке выдаём «Платёж принят банком,
   подтверждаем» и перечитываем статус 2–3 раза. Никаких «оплачено» по параметру URL.
5. Сначала тестовый режим (тестовые ключи), потом боевые.
6. **Проверить во вторник, до 14:00:** ЮKassa требует ИП или самозанятость клиента. Если
   её нет — включаем режим «без онлайн-оплаты» (пункт 15), не теряя неделю на
   выяснение. Это риск №1 по оплате.

## 8. Аналитика рекламных каналов

- На первой загрузке страницы JS читает `utm_source/medium/campaign/content/term` +
  `referrer`, шлёт `POST /api/track/visit/`, пишет cookie `bc_utm` на 30 дней
  (first-touch, не перезаписывается).
- UTM-метки заказчик ставит прямо в рекламной ссылке: `?utm_source=yandex&utm_medium=cpc&utm_campaign=tor`.
  Сокращатели и Bitly не нужны — любой редирект со стороны только теряет метку. Готовые
  ссылки для каналов перечисляем в `docs/CLIENT_GUIDE.md`.
- Экран в админке «Каналы»: заказы, выручка, средний чек, конверсия (визиты → заказы →
  оплаты) по каждому `utm_source` за период + фильтр по датам.
- Метка верификации Яндекс.Метрики в `<head>` (счётчик подключается флагом в `.env`) —
  без неё Метрика не примет визиты, а сценарий ТЗ «сколько заработали с рекламы» без
  неё не считается. SEO-минимум (`robots.txt`, `sitemap.xml`, Open Graph, description)
  в срок не входит: трафик приходит по рекламным ссылкам с UTM, а не из поиска.

## 9. Админка

Кастомизированный Django admin в стиле сайта (логотип, цвета, шрифты) **+ два своих
экрана**:

1. **Сводка** — 4 плитки (заказы, выручка, средний чек, конверсия) + таблица по каналам
   + динамика по дням.
2. **Доска заказов** — таблица с фильтрами; карточка заказа = «что готовить»
   (спецификация на экране, срочные помечены «+20%») + «куда везти» (адрес,
   дата и время) + «телефон» (кликабельный) + комментарии + смена статуса и
   времени доставки. Печать листа сборки не делаем.
   Статуса всего три, поэтому в списке две кнопки: «Отметить оплаченным»
   (`new → paid`, штатно этот переход делает вебхук ЮKassa, кнопка — только если
   вебхук не пришёл) и «Выполнен» (`paid → delivered`). Кнопки отмены
   нет — работаем по предоплате. Очередь пекарни — оплаченные заказы
   по `delivery_date` + `delivery_time`.

Плюс стандартные списки Django admin: заказы, торты, опции и цены, промокоды. Правил
доставки в списках нет — они константы в `settings.py` (раздел 3).

## 12. Деплой на FirstVDS

**Владелец деплоя — В (DevOps).** Деплой автоматический и запускается **при каждом
пуше в `main`**: таймер на сервере проверяет `main`, новый коммит → `deploy.sh`.
Не А: у А и так весь бекенд. Если деплой сломался — чинит А. Несделанный деплой
не ждут: сайт просто отстаёт на один коммит.

> **Деплой не начинается первым шагом.** Шаг 1 — только локально, сервер поднимается
> на шаге 5 (`install.sh` один раз). До этого момента автодеплоя на сервере нет,
> пуши в `main` просто копятся в репозитории.

### Что есть на сервере (замерено 30.09.2026, не взято из этого плана)

Раздел изначально описывал сервер по предположению и в шести местах разошёлся с
реальностью. Параметры ниже — из обследования бокса, а не из пожеланий.

| Что | Значение | Откуда известно |

| Ядер | **1** | `nproc` |

| Подкачка | zram 899 МБ, занято ~596 МБ | `swapon --show` |

Отсюда пять решений, которые нельзя вывести из этого плана без обследования:

1. **Порт 8004, а не 8000.** Порт из ранней редакции этого раздела занят главным
   сайтом `kislyakov.pro`. Перезапуск соседа недопустим.
2. **Два gunicorn-воркера, а не три.** Одно ядро не даёт выигрыша от третьего
   процесса, а свободной RAM ~740 МБ, и на всём боксе уже едят 381 МБ.
3. **Таймер systemd, а не cron.** Cron на боксе не установлен, и cron-строка
   самого пакета certbot содержит `test ! -d /run/systemd/system` — то есть под
   systemd она всё равно не исполняется. Периодику соседей смотрят
   `starburger-clearsessions.timer` и `selfstorage-notify.timer`: сделано так же.
4. **Бэкап через `sqlite3.backup()`, а не `cp`.** WAL включён в `settings.py`, при
   копировании живого файла часть подтверждённых данных может не попасть в копию.
   Ранняя редакция обещала бэкап, которого в реальности не делал ни один деплой
   соседей, — отсюда и несуществующий `/opt/backups`.
5. **`EnvironmentFile=`, а не `Environment=`.** У соседа `dossier.service` ключ
   записан прямо в юните без кавычек, и systemd не может его разобрать: в значении
   есть `*`, `^`, `%`, `$`, `(`, `#`. Итог — `DJANGO_SECRET_KEY` для `dossier` не
   задаётся вообще. У нас ключ живёт в `.env` и закавычен, как у двух здоровых
   соседей.

### Подъём сервера

`deploy/install.sh` — один раз, в первый день шага 5. Идемпотентен: пакеты
доустанавливаются только если их нет, существующий `.env` не перезаписывается,
уже выпущенный сертификат продлевается, а не запрашивается заново. Порядок важен:
сначала сервис, потом nginx, потом certbot — HTTP-01 проверяется уже на живом
vhost, и `/opt/backups` с `/var/log/bakecake` создаются до первого деплоя, иначе
`cp` и открытие лог-файла gunicorn'ом падают на пустом месте.

`.env` **не создаётся копированием `.env.example`** — в шаблоне `DEBUG=1` и
`ALLOWED_HOSTS=localhost`, такой файл даёт `400` на публичном домене и утечку
traceback. `install.sh` генерирует ключ и пишет домен сам.

### Деплой одной командой

`deploy/deploy.sh` — то, что зовёт и таймер, и человек:

```bash
cd /opt/bakecake
BACKUP="/opt/backups/db-$(date +%F-%H%M%S).sqlite3"
.venv/bin/python - "$BACKUP" <<'PY'
import sqlite3
import sys

source = sqlite3.connect("/opt/bakecake/backend/db.sqlite3")
target = sqlite3.connect(sys.argv[1])
source.backup(target)
PY
git pull --ff-only origin main
.venv/bin/pip install -q -r requirements-server.txt
cd /opt/bakecake/backend
../.venv/bin/python manage.py collectstatic --noinput
../.venv/bin/python manage.py migrate --noinput
../.venv/bin/python ../scripts/seed_demo.py
systemctl restart bakecake
```

Отличия от `~/deploy_star_burger.sh` — соседского рабочего деплоя, с которого
взяты порядок шагов, запуск venv бинарниками напрямую (без `source activate`) и
короткое имя юнита в `systemctl restart`:

- `git pull --ff-only origin main` вместо голого `git pull`;
- `requirements-server.txt` вместо `requirements.txt` — gunicorn не нужен на
  локальной машине;
- бэкап БД, которого у соседа нет;
- **certbot в деплой не входит**: сертификат продлевает `certbot-renewal.timer`,
  звать `certbot renew` на каждом пуше — лишняя сетевая зависимость;
- `seed_demo` не выкидывается, как в соседском скрипте, потому что у нас в БД
  только она.

> **Два места, на которых спотыкается скрипт.** `manage.py` лежит в `backend/`,
> поэтому перед `migrate` обязателен `cd /opt/bakecake/backend`. И `seed_demo.py` —
> **не** management-команда: он лежит в `scripts/`, вне приложений, поэтому
> вызывается как `python ../scripts/seed_demo.py`, а не `python manage.py seed_demo`.
> Проверяется только на сервере, поэтому деплой не должен доезжать до сломанной
> строки второй раз.

**`seed_demo` идемпотентный.** При каждом деплое `update_or_create` для демо-каталога,
цен, промокода и демо-заказов/визитов — приводятся к текущим моделям. Реальные заказы
и оплаты клиента **не трогаются** и не удаляются, `seed_demo` можно безопасно запускать
на боевой базе под каждым пушем. Пароль существующего админа сид тоже не сбрасывает —
иначе пароль на сервере менялся бы на каждую рассылку.

### Проверка нового коммита

`deploy/auto-deploy.sh` — его зовёт таймер. Ничего не деплоит само, только
сверяет и передаёт управление:

```bash
cd /opt/bakecake
git fetch --quiet origin main
if [ "$(git rev-parse HEAD)" != "$(git rev-parse origin/main)" ]; then
  /opt/bakecake/deploy/deploy.sh
fi
```

Сравнение именно с `origin/main`, а не `@` против `@{u}`: при расхождении
ветки последняя проверка всегда даёт «есть изменения», и таймер деплоит
бесконечно. Форс-деплой текущего состояния без нового коммита — `deploy.sh`
руками, он не проверяет ничего.

### Таймер

`bakecake-autodeploy.timer` + `bakecake-autodeploy.service` — по образцу
`selfstorage-notify`, тот же интервал в 3 минуты. `Persistent=true` из соседских
юнитов **не переносится**: он работает только с `OnCalendar`, а здесь
`OnUnitActiveSec`, поэтому ставятся `OnBootSec` и `AccuracySec`. Вывод сервиса
идёт в `/var/log/bakecake/deploy.log` через `StandardOutput=append:` — так же,
как у соседа, а не в syslog.

### nginx

`deploy/nginx.conf` содержит **только HTTP**. Второй vhost с `return 301` и
`return 404` на :80, а также `listen 443 ssl` и пути к сертификату дописывает
`certbot --nginx` сам — ровно как в трёх соседних конфигах. `default_server`
не объявляется: его держит `dossier`, и перехват чужого умолчания сломал бы
главный сайт.

Блок `location /media/` у соседа есть, у нас его нет и не будет: в `settings.py`
нет ни `MEDIA_ROOT`, ни `MEDIA_URL`, загруженных файлов в MVP не предусмотрено.
`alias` ведёт на `/opt/bakecake/backend/staticfiles/`, а не на
`/opt/bakecake/staticfiles/` как у соседа, потому что у нас `BASE_DIR` — это
`backend/`.

`proxy_set_header X-Forwarded-Proto $scheme` в конфиге есть, и именно поэтому в
`settings.py` обязателен `SECURE_PROXY_SSL_HEADER`: без него Django считает схему
`http`, ждёт `Origin: http://bakecake.kislyakov.pro`, а браузер шлёт `https://`,
и **любой POST, включая форму входа в админку, падает с 403 CSRF**. Ни один
сосед этого не настроил — у них просто нет POST-форм под HTTPS, поэтому проблема
не всплывала.

## 14. Границы MVP — что режем ради срока

| Режем | Почему можно | Почему не жалко |
|---|---|---|
